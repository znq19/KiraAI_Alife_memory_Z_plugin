# Alife Memory Z · 长期记忆·Z

> 让每一段记忆都有来处，每一段故事都有归处。

一个给 KiraAI 用的**长期分层记忆**插件：把 Alife 的记忆系统移植改造过来，让 Bot 记得住、想得起、说得清，而且记忆全部可以在网页端热改和监控。

---

## 前言

这个插件核心设计部分学习和借鉴于 [Alife](https://github.com/BDFFZI/Alife) 项目的官方记忆系统。我一直很羡慕我朋友为他的桌宠真央做出的表现良好的长期记忆方案，记得不少，回忆也不少。虽然我技术很有限，但最后还是算终于做出来了。希望能对大家有帮助。让每一段回忆，都有来处；每一个故事，都有归处。

---

## 30 秒看懂它能做什么

| 能力 | 说明 |
| --- | --- |
| **记得住** | 聊天内容、图片/语音识别结果、Bot 自己的回复、工具查询结果都会变成记忆 |
| **想得起** | 每轮自动把相关记忆喂给模型；模型也能用工具主动去翻旧账 |
| **说得清** | 每条记忆都带**时间、来源会话、来源用户、存档 ID**，不会把别人的经历说成你的 |
| **改得动** | 网页端可以直接改摘要、改画像、改关系、改名字，改完立刻生效，不用重启 |

## 记忆是怎么工作的

### 1. 三层结构：原始经历 → 压缩存档 → 永久记忆

```
L0 原始记录（原文，永久保留：只剥协议外壳，人说的话一个字不少）
 │  同一会话攒到 50 条 → 压缩最早的 40 条（剩下 10 条原文留作尾巴）
 ▼
L1 摘要（带时间范围 + 子存档 ID）
 │  上层攒到 4 条 → 压缩最早的 3 条
 ▼
L2 … L8（最多 8 层）

L100 永久记忆（不参与自动压缩，只能由 Bot 主动 Memorize 或你在网页端添加）
```

- **层级只表示"被压缩了几次"，不代表重要程度**。
- 被压缩掉的原文**不会删除**，摘要里保留子存档 ID，随时可以顺着 ID 读回最初的对话。
- `Forget` 只是把记忆移出"活跃记忆"，原文依然读得到。
- 攒够阈值后**不是每次都触发**，而是按 `probability`（默认 0.8）概率启动，避免一直烧模型。

### 2. 每轮给模型什么

每轮对话，插件会在**本轮用户消息里、用户真正说的话之前**插入一个 JSON 记忆块。默认是**情境化注入**（`inject_mode=situational`）：

| 档位 | 内容 | 何时出现 |
| --- | --- | --- |
| 常驻 | 参与者、Bot 身份、人物/群名、约定与偏好类事实（`commitment` / `preference` / `profile`）、最近 1–2 条压缩存档 | 每轮 |
| 触发·提到人 | 消息**提到某个已登记的名字**（含消息里的昵称）→ 带回关于这个人的事实（含跨会话、跨用户） | 只在相关时 |
| 触发·提到词 | 消息内容与**事实内容词面匹配**（中文按 2 字切分）→ 带回命中事实，默认门槛 2 分，最多 `top_k` 条 | 只在相关时 |
| 触发·回忆词 | 命中「记得 / 之前 / 上次 / 曾经」→ 放宽一档（`top_k×2` 条），并追加一句「可按需检索存档」 | 只在相关时 |
| 存档 | 用整句话词面检索**其他会话**的存档摘要；默认**连已归档的旧记忆一起搜**，同分时常驻优先 | 每轮（`recall_scope` 非 `session` 时） |
| 按需 | 细节由 `SearchMemoryArchive` / `ReadMemoryArchive` 取 | 模型自己判断 |

这样既有「碰到谁、碰到哪个词就想起相关的事」的手感，又不会每轮把整库事实倒进上下文。软删（审计撤回 / 合并掉）的事实、冷归档与超龄淡出的旧存档永远不参与自动召回。想回到旧的全量行为，把 `inject_mode` 设成 `full` 即可。

事实只带**判断和追溯需要的字段**（类别、主体、内容、关系、重要度、最新一条来源指针 `src`、记录日期）；内部簿记（指纹、版本、合并标记、审计时间等）不再进入上下文。`reason` 只留给审计模型和网页端，不再注入给对话模型。

**还没压缩的原始对话（L0）默认不进这个块**——KiraAI 自己的上下文里本来就有最近若干轮，再注入一遍只会让上下文膨胀、还挤占提示词缓存。需要时模型用 `SearchMemoryArchive` 主动检索，或 `ReadMemoryArchive(id)` 按 ID 读回；想恢复旧行为可以打开 `inject_recent_raw`。

同时往系统提示里追加一段**固定不变的**工具使用规则。这两处都设置 `persist=False`——**不会写进 KiraAI 的聊天历史**。

### 3. 模型可以主动回忆（工具）

| 工具 | 作用 |
| --- | --- |
| `SearchMemoryArchive` | **找记忆 / 取记忆**：给 `ids` 按短码读回存档（含子存档、`include_content` 读原文）；给关键词/时间/层级搜索，默认只给"这个会话还没给过"的新内容 |
| `GetProfile` | **看人 / 看全局**：给 `subject`（实体 ID 或名字）看画像、名字历史、按类别事实与关系；`view=names` 只列现名与曾用名；都不给则返回总体统计与一批未见过的画像/偏好/约定 |
| `Memorize` | 保存**必须每轮在场**的约束或身份（可带 `category` / `importance`）；能被既有事实覆盖时会直接返回那条事实，不重复占常驻席位 |
| `CorrectMemory` | **维护记忆**（都要写 `reason`）：`update` 改字段、`merge` 合并重复、`delete` 软删、`restore` 恢复、`archive` 移出常驻、`refresh` 刷新昵称、`tidy` 请系统整理永久记忆 |

**同一会话只给新情报**：搜索默认排除这个会话已经给过的记忆，`already_seen` 告诉你跳过了多少；想看旧的可以用 `allow_seen=true` 或直接按 ID 读。

**检索结果的紧凑形态**（v2.7.0 起，为省 token 也是为了让模型少抄错）：

```json
{"ok": true, "total": 98, "next_page": 2, "already_seen": 12,
 "who": {"周武": "qq:769690776"},
 "items": [{"i": "k7f3a9", "t": "09-08 22:39", "s": "聊到师傅和星月的事…", "bot": 1, "arch": 1, "u": ["周武"]}]}
```

- `i` 是 **短码**（6 位），`ReadMemoryArchive` / `Forget` / `CorrectMemory` / `exclude_ids` 都同时接受短码和完整 ID —— 完整 ID 有 31~71 字符，抄错一位就查不到；
- `who` 把**完整账号整批只给一次**（名称 → 完整 ID），条目里用昵称引用，需要汇报或核对时从这里取；
- 默认值一律省略（`bot`/`arch`/`mem` 只在为真时出现），时间只留 `MM-DD HH:MM`；
- 摘要会做安全清洗：剥掉最外层 `<msg>`/`<text>` 包裹（**多段消息保留换行边界**）、压缩换行与多余空格；
  被折行插进中文词里的**孤立空格**会合并；**正文里字面出现的 `<text>`、`<` 等原样保留**；
  表情包描述与引用原文会截断（细节可用 `ReadMemoryArchive` 读全文）。
- **真实的空格不会被误伤**：① 连续被空白隔开的写法（`很 重 要`、`请 注 意`）视为刻意强调，原样保留；
  ② 实体表里**名字真的带空白的昵称**（`星 月`）会作为保护名单传入，渲染时不受空白归一影响；
  ③ 以上都只作用于「给模型看的那一份」与检索打分，**数据库原文一个字都不改**。
- 关键词检索同样做了空白归一：库里存着 `翅 膀`，用 `翅膀` 也搜得到，反过来也一样。

日志实测：两页共 60 条真实记录，返回体 **22,582 → 9,256 字符（−59%）**。

### 4. 后台整理（压缩 + 审计 + 永久记忆整理）

- **什么时候会压缩**（三条自动触发 + 手动）：
  · **攒够 `compress_rounds`（默认 12）个完整轮** ✓（活跃会话正常走这条）
    —— 一次能提炼几条事实**随本批消息密度伸缩**（约每 6 条消息 1 条，最多 12 ✓）
  · **冷会话**：`compress_stale_after_days`（默认 3 天）**且** `compress_idle_after_hours`（默认 6 小时）
    **同时满足** ⇒ 门槛降到 1 ✓（只看其一会把"还在聊但有老记录"或"刚停下但内容很新"的会话也提前压 ✓）
  · **迁移数据没有"轮"** ⇒ 退回**按条**（B4 ✓）；已是知识类的迁移内容则在扫描时**就地归档**（0 次模型调用 ✓）
  · 触发点：调度器每 30 秒（掷 `probability`）/ 启动·每 15 分钟·迁移后（不掷骰，≤2 会话定向兜底）/
    每条消息后（掷 `probability`）/ 手动（工作台、bot 工具 —— **无闸门且可无视冷却** ✓）
  · 每个任务最多连压 `compress_batches_per_job`（默认 3）批；每批只受**字符预算**（默认 20000）限制，
    且**绝不切半轮** ✓；同一会话每 30 分钟最多降门槛一次 ✓
  · **空转的自动任务不打日志、不占工作台** ✓（"机械判断、没花钱"的不该占版面 ✓）；有发起方的照常显示 ✓
- **压缩**（压缩与合并模型）：按上面的层级规则把原始记录压成摘要；一次任务会连续排空积压，不会每轮都花钱。
- **永久记忆整理**（每 2 小时检查一次）：永久记忆超过**条数上限**（默认 10）或**字符预算**（默认 3000）时，
  后台请模型逐条判断 —— `keep`（继续常驻，可顺带修正类别/重要度）、`extract`（这条信息已能被事实覆盖 →
  提炼成事实后移出常驻）、`archive`(不再需要常驻)、`split`（一条里既有约束又有可提炼内容 → 拆开：约束留下、其余转事实）。
  **只归档不删除**：原文、版本、回收站都在，可一键"取回上下文"。条数上限触发时会一次排空积压。
- **召回去重**：每轮把相关事实带回来时，顺手做一次零成本的本地相似度判定——同主体、**同类别用 0.25**（与写入侧一致），
  **同主体、跨类别用 0.4**（同一件事被记成不同类别时靠它发现）；命中就标记并投递给后台合并队列
  （**不阻塞回复、不多花模型调用**），**本轮照常完整注入，从下一轮起被合并的那条才不再出现**。
- **合并判定有三个动作、没有 keep**：`merge`（合并）/ `relabel`（只统一类别）/ `drop`（删掉冗余的，软删可还原）；
  默认附上各条事实的**来源原文**作为判定依据（配置 `fact_merge_evidence` 可关掉省 token）。跨主体一律不合并。
- **写入时合并**（压缩与合并模型）：新事实入库时先在**同一会话 + 同一主体 + 同一类别**里找相似旧事实，达到阈值就**强制合并**（冲突以时间较晚的说法为准，模型输出不可用时用原文拼接兜底）；身份/偏好/关系类事实允许跨会话合并成一条全局记忆。合并完成前这条新事实不会进入检索，避免对话里同时看到重复。
- **审计**（审计模型）：定时检查事实是否重复/矛盾，提出修正或合并。默认**每 2 小时**一轮，每轮最多 `worker_count` 个会话、每个会话 ≤20 条；同一条事实距上次审计超过 `audit_recheck_days`（默认 7 天）才会再审，另有 `audit_daily_calls` 每日调用上限兜底——**没有待审事实就不会调用模型**。
- `dedupe` 任务用审计模型合并相似的永久记忆（检测到相似就合并，可配置关闭）。
- 所有任务都在后台队列里跑，默认 2 路并发，可热改；失败会保留原文并自动冷却重试。

### 5. 人物、画像与关系

- 名字来自新消息的昵称和会话标题，用**稳定 ID** 关联现名、曾用名、来源和观察时间；同名不会乱合并。
- 从记忆里聚合出**画像**（性格、偏好、关系、事实）和**关系三元组**，网页端有星图可以看。
- 「人物与群名」列表**不点开就有**：一行画像摘要（按重要度取前几条）+ 事实/关系/会话统计；点开可以看按类别分组的事实、关系连线和名字历史，每条都能编辑或**恢复历史版本**。
- Bot 也能直接查：`GetProfile("萤火")` 一步返回聚合画像，不必再自己拼 `MemoryNames` + `MemoryOverview`。
- 第三方插件（比如提醒插件）发的合成消息带占位昵称（`提醒任务所有者` 等），会被自动忽略，不会污染人物称呼。

### 6. 为什么不拖慢、不破坏缓存

- 系统提示里**只加一段固定文本**，每次请求逐字节相同；
- 所有会变化的内容（存档、事实、画像、时间、会话状态）都放在**本轮用户消息的最前面**，设置 `persist=False`；
- **不改写** KiraAI 的聊天历史和请求里已有的消息。

所以「系统提示 + 历史」这段前缀始终稳定，提示词缓存（prefix cache）能命中，只有最后一条消息是新的。

## JEV 决策模型（可选增强，默认全关）

把一个**专用决策模型**（TypeSafe Jev / 兼容中转）接进来，替我们做几处「判定」——
它**不生成任何文字**，只回答「是不是 / 哪一类 / 有多相关」，所以便宜、稳定、不会跑偏。

### 它在哪些环节起作用

| 环节 | 它做什么 | 形态 | 时机 |
| --- | --- | --- | --- |
| 被动召回 | 从候选里挑出**该注入**的（清明显无关 + 重排） | 排 + 筛 | 注入点，带硬预算 |
| 被动召回 · 触发 | 关键词没命中时判断「是不是在让我回忆往事」⇒ 放宽召回 + 提示 | 补充判断 | **同一次调用**，零额外延迟 |
| 主动召回 · 查档案 | 搜索结果按相关度**重排 + 筛**（筛掉的**不标「已见」**⇒ 换个词还能搜到） | 排 + 筛 | 模型调工具时 |
| 主动召回 · 看画像 | 事实按**当前对话**重排（对抗 `limit` 截断 ⇒ 顺序决定看到哪些） | 只排 | 同上 |
| 主动召回 · 未见事实池 | 按当前对话重排（顺序决定先看哪些、哪些被消耗） | 排 + 筛 | 同上 |
| 合并事实 | 组内细化：该合的合、**低价值重复进回收站**、会稀释的**摘出去** | 路由 | 后台 worker |
| 审计 | 先筛可疑对（重复/矛盾/过时）；**全筛过且干净**才跳过整次审计 | 预筛 | 后台任务 |
| 写入事实 | **只下调**低价值事实的重要度（`无价值→1`、`次要→3`），**只压不抬** | 定级 | 后台任务 |

### 怎么开

1. 「设置 → 提供商」注册一个**类 JEV 决策模型**（官方 `https://api.typesafe.ai`，或你自己的中转）
2. 本插件设置里选中它（`jev_model`）——**请正确选择类 JEV 决策模型，误选其他将无法正常使用**
3. 打开 `jev_enabled` 与需要的那几个开关（`jev_recall` / `jev_merge` / `jev_audit` / `jev_importance`）

### 安全保证（都可复现）

- **默认全关**：不开时行为与之前**逐字节一致**（有测试守着）
- 客户端**永不抛异常**：失败 / 超时 / 不可用 ⇒ 一律回退原有逻辑；连续失败自动熔断
- **调用只在需要时发生**：被动召回只在「确实要回复」时；宿主判定 `discard` 的消息完全不预热
- **预算可调**：`jev_timeout_ms` 默认 5000ms，超时立刻用原排序
- 主动召回**只排序 / 只清明显无关**；筛掉的不进「已见」⇒ 不算丢
- 合并正文仍由大模型写 —— JEV 不生成任何内容

### 实测数据（真机，2026-09-24）

- **召回筛选**：20 条候选（含 8 条与对话**字面零重合**）⇒ 该注入的**全部捞回**、无关的 8 条全滤掉，**零漏召零误召**
- **阈值标定**：无关簇 0.03~0.07 / 相关簇 0.15~0.83（有 ±0.06 抖动）⇒ 取 **0.10** + 保底条数
- **触发判定**：改写说法（「我们聊过的那个火锅店叫什么来着」）0.97 命中；非回忆请求 0.01
- **合并路由**：纯重复 → 回收站；有价值补充 → 合并
- **重要度**：`工作日吃素→次要(3)`、`哈哈好的→无价值(1)`；高价值**不写回**
- **决策留痕**：插件数据目录 `memory_jev_decisions.jsonl`（可回溯、可二次标定）

### 注意

- 阈值是用**中转**端点标定的；换官方 API 建议先看几天日志再微调
- 别给 JEV 的提供商挂「只转发 OpenAI chat 协议」的加速/代理通道 —— JEV 走 `/v1/systemone`，转发不过去
- 与加速器类插件共存无冲突：加速器接管的是宿主的 `chat` 客户端层，而 JEV 是**直连**端点

## 安装

1. 把本仓库内容（至少 `main.py` / `manifest.json` / `schema.json` / `web/` / 其他 `.py` 文件）放进 KiraAI 的 `data/plugins/alife_memory_z/`，或在插件管理里安装本仓库的 ZIP。
2. 安装依赖：`pip install -r requirements.txt`（KiraAI 自带 FastAPI 和 Pydantic，无需另装）。
3. 在 KiraAI 插件管理里启用，侧边栏会出现 **长期记忆·Z**。

> 核对过的 KiraAI 核心版本：**v2.34.1**（提交 `cad046f`）。没有设置 `core_version` 门槛，兼容性通过真实接口测试确认。

## 第一次使用（推荐设置）

1. 侧边栏 **偏好设置** → 确认 `启用` 和 `记录对话与感知` 打开。
2. `Bot可访问范围`：想让它跨群、跨私聊回忆就保持 `global`；只想在一个会话里回忆就选 `session`。
3. `压缩模型`：默认用快速模型即可；经常超时换更快的。
4. `审计模型`：默认用主模型，建议选理解准确的那个。
5. **同装会话合并/压缩类插件（KSM / ADS / Context Condensation）时，把 `上下文字符预算` 从 24000 调到 8000 左右**（原因见下方兼容性）。
6. 想省钱：`向量检索` 保持关闭（默认），它只影响语义搜索，关键词搜索不受影响。

## 网页端（侧边栏）

| 页面 | 用途 |
| --- | --- |
| 概览 | 记忆/事实/画像/关系数量、迁移与互斥状态、载入动画 |
| 存档管理 | 按会话、用户、类型、标签、层级筛选；读原文、改摘要、软删除 |
| 画像与关系 | 画像卡片、关系星图、证据回溯 |
| 后台任务 | 手动排队压缩/审计/合并/重建索引；每条任务可点「明细」看这次处理了哪几条并直接编辑 |
| 回收站 | 已删除的事实/存档与冷归档，按维度查看、搜索、还原或编辑 |
| 偏好设置 | 所有配置项；文案类字段旁边有「恢复默认」 |

**存档管理的会话筛选**：选中某个会话后默认**只显示该会话自己的记忆**。旧插件迁移来的全局记忆、以及跨会话共享给本会话参与者的记忆，需要勾选「含跨会话记忆」才会一并列出（此时它们会带 `跨会话` 标签）。

**搜索的两种语义**：存档管理页搜的是**存档摘要**（内容匹配）；画像与关系页勾选「按内容搜」后，输入框变成**事实内容**搜索，配合维度筛选可以缩小到某一类。

**星尘特效**：页面背景有星点与流星（同一色系随机变色），顶栏 `✦` 可关闭；系统开启「减少动态效果」时会自动停用。

**人物与群名的批量拉取**：名字页的「批量拉取姓名」按钮会先弹二次确认——「只补没有名字的」只处理缺名的号码、已有名字一律跳过；「全更新」则连已有名字一起用平台当前昵称更新，旧名保留在曾用名里、可一键恢复。

**三个维护按钮**（后台任务页底部）：

- **清理历史工具记录**：把工具结果压成 240 字预览，并移除"读自己记忆"的回声记录（原文保留）；
- **修复被改写的昵称**：第三方插件把昵称写成 `提醒任务所有者` 之类时，恢复上一个正常称呼；
- **清理历史播种记录**：删除"安装插件时抄进来的旧对话"，与会话合并插件同装时尤其有用（软删除，原文保留，且清理后不会重新播种）。

> 2.3.0 起，如果检测到会话合并/压缩插件、且库中存在**来源无法确认**的播种记录（旧版本遗留），概览页会自动弹一条提示条，提供「去清理」和「保留，不再提醒」——不会自动删除任何记忆。

## 与其他插件一起用

| 插件 | 会不会冲突 | 说明 |
| --- | --- | --- |
| KSM 会话合并 `kira_session_merger` | 不冲突 | 它注入跨会话**原始对话**，我们注入跨会话**记忆档案**，互补 |
| ADS 自动压缩 `auto_delete_session` | 不冲突 | 它压缩 KiraAI 自己的会话历史，我们的记忆库是独立副本 |
| Context Condensation | 不冲突 | 它写回摘要块、明确不动系统提示；实测不会误读我们的记忆块 |

三点要知道：

1. **不会互相禁用**：我们的互斥名单只有两个老记忆插件（`kira_plugin_simple_memory`、`kira_plugin_kiraos`）。
2. **旧历史播种保护（2.3.0 新增）**：KSM 会把别的会话的对话合并进当前请求，如果这时把整段请求历史抄进记忆库，就会"把别人的经历记成你的"。所以默认 `bootstrap_seed=auto`：**检测到 KSM / ADS / Context Condensation 启用时跳过播种**，只记装插件之后的内容。
   - 检测到合并插件、且库里有**旧版本遗留**、来源无法确认的播种记录时，概览页会提示你核对（可一键保留不再提醒），**不会自动删数据**。
3. **上下文预算互相看不见**：这三个插件的压缩阈值只统计 KiraAI 自己的历史，看不到我们注入的记忆块（最大 24000 字符）。同装时建议把 `context_chars` 调到 **8000 左右**，或给 ADS 的 `max_tokens` 留出余量。

> 另外，KSM 和 ADS 默认都会自动禁用 Context Condensation（`disable_ccs`）——这是它们三者之间的策略，与本插件无关。

## 常见问题

**Q：为什么它好像不记得？**
依次检查：`enabled` 和 `capture_enabled` 是否打开 → `recall_scope` 是否够大（跨群回忆要 `global`）→ `context_chars` 是否被压得太小 → 这段记忆是不是被 `Forget` 或冷归档了（用 `SearchMemoryArchive(include_archived=true)` 或按 ID 读）。

**Q：会花很多钱吗？**
压缩和审计会调模型，但只在攒够阈值后按概率触发；向量检索默认关闭。想更省：把 `probability` 调低、`audit_enabled` 关掉、用便宜的快速模型。

**Q：它会改 KiraAI 自己的聊天记录吗？**
不会。我们只读不写宿主历史，记忆存在自己的 SQLite 里。

**Q：和 KSM 一起用，第一次装上为什么没继承旧对话？**
这是 2.3.0 的播种保护：KSM 在改写上下文时，历史里可能混着别的会话，直接抄进来会串味。`bootstrap_seed=always` 可以强制播种，或在没装 KSM 时先播种。

**Q：旧记忆插件的数据怎么办？**
默认开启安全迁移：只读接入三类旧插件的数据，校验后导入，**原文件一律保留**；

| 旧插件 | 数据位置 | 说明 |
|---|---|---|
| 默认记忆 simple_memory | `data/memory/core.txt` | 老格式逐行解析 |
| KiraOS | `data/memory/{entities,global}/**` | TOML 树 |
| **海马体记忆** hippocampus | `data/plugin_data/kira_plugin_hippocampus_memory/memory/**` | 与 KiraOS **同构**，复用同一解析 |

三者布局一致（`global/{facts,self,skills}` + `entities/<类型>_<编码ID>/{facts,reflections,skills}` + `profile.json`），
所以**不需要额外装 KiraOS** ✓ 直接读数即可。迁移成功后才停用冲突插件；**个别文件读不了（语法坏、编码不对、字段脏）会跳过并在报告里逐条标出**，不阻塞迁移——这与旧插件自己对坏文件的宽容度一致（KiraOS 连坏 TOML 都是跳过不阻塞的），源文件只读保留、导入幂等，以后修好仍会被补扫回来。只有**整个来源一条都没接上**、或迁移本身（导入/停用/收尾）出错时，才暂停自身并保持旧插件启用。

迁移在**后台执行**，不会卡住插件加载：启动后先在后台跑，期间记忆功能暂停（`migration_blocked`），完成后自动恢复，状态在概览页可见。如果旧记忆源文件没有变化、也没有旧插件在运行，启动时会**直接跳过扫描**（只 stat 文件、不解析），不会每次都重读一遍。

### v2.18.26 — 性能优化二次审查：抓到并修掉一处"预检误杀"

### v2.18.25 — 召回路径性能审计：每条消息省掉 ~60 ms（压缩闸门预检 + active 缓存）

**先量再说**（一个 3000 条记录的活跃群，全部实测）：

| 操作 | 耗时 |
|---|---|
| `active(sid)`（最热查询）| **65 ms**（SQL 物化 32 + 转 dict 32）|
| `active(sid) + compression_plan`（压缩闸门）| **71 ms** |
| `compress_probe`（新，只回 3 个数）| **6 ms** |
| 命中缓存的 `active(sid)` | **0.02 ms** |

**查出两处"每轮白付"**：
1. **同一条消息里 `active(sid)` 被调 2~3 次**（`on_request` 开头一次 + 回复后压缩闸一次）

- `active(sid)` 加 **1.5 秒 TTL 缓存**；失效判据用 `connect()` 里的 `total_changes`

- 压缩闸门先用 **`compress_probe` 预检**（只回 非永久行数 / 最早 end / 最新 end，走覆盖索引）
  **只放行不否决** ⇒ 判定结果与原来**完全一致**（随机用例对拍 ✓ 口径改坏必报红 ✓）

**留下的**：`active(sid)` 那 65 ms 是"行物化 + 转 dict"的固有成本，

### v2.12.0 (2026-09-12) — 默认更早整理 + 落库净化（外壳/思考块/空消息）🧹

**① 默认值：更早开始整理。** 原先是照抄 Alife 原版的 `100 / 70 / 0.4`，对短会话来说太晚——

概率的三个检查点（Bot 每次回复后 + 调度器每 30 秒对所有会话各一次）意味着低于 1 也只是
晚几十秒，不会"永远不整理"。⚠️ 改的是**默认值**，已有配置不会被动，需要手动改或重置配置。

**② L0 落库前剥掉协议外壳。** 「外壳」指的是 `<msg>`/`<text>`/`<msg/>`/`</msg>` 这类
**进模型的那版文本**的容器——不是人说的话。代码里本来就有 `clean_text()`（`_strip_wrappers`），
但它只用在"给模型看的样子"上（压缩输入、工具读回），**落库路径没走**，于是 XML 外壳一路进了
原文、摘要和压缩输入。现在落库也走同一套清洗（`clean_text` 只吃标签、不吃标签外的字符，
正文里字面写的 `<text>` 原样保留）。各种写法都认：
`<msg> <msg/> <msg /> <msg attr="1"/> <MSG/> </msg> </msg > <text/> <text></text>`。

**③ 思考块不进记忆。** Agent 的 `<reasoning>…</reasoning>`（z 插件提示词里要求的推理标签）
原本被当成正文存进 L0，会被压缩进摘要与事实——例如「主人叫收声，立刻听话」这种内部指令
进了长期记忆就很糟。现在 Bot 的输出落库前先剥思考块：成对（跨行/带属性/大小写）、未闭合
（截到下一个 `<msg` 之前）、自闭合都认；**未闭合且后面没有 `<msg>` 时只删标签、正文一个字不动**
（宁可留下思考，也不丢正文）。

**③b 给模型的出口也一并收紧。** `model_text()`（压缩输入 / 工具读回 / 注入的统一出口）
与落库**共用同一套外壳规则**，所以这次所有标签修复对模型侧同时生效；此外它**比落库多剥一层
思考块**——落库保原文（用户有可能真的引用了 Bot 的思考块，那是他说过的话），但发给模型的内容
一律不带内部推理。这样即使存量清理没跑到，模型也不会被思考块污染。

**④ 没有实际发言就不建记录。** 只输出 `<msg/>`（就是 z 插件里"这次不回复"的写法）、
或渲染不出内容的消息，清洗后是空的——它们没有信息量，却会计入压缩阈值、白占压缩输入。
现在这类不再建 L0 记录（有工具调用的照记，只记工具摘要）。

**④b 工具返回也走同一套。** 工具感知结果落库前同样剥外壳（夹带的 `<msg>` 之类不该进记忆），空结果不建记录。

**⑤ 存量清理。** 升级后启动时会**自动跑一次**（只跑一次，记录在 `meta.capture_scrub`）：
L0 走落库同一套清洗，L1+ 的摘要**只剥思考块**（那是模型写的散文，避免误伤尖括号内容），
同步重算检索索引体。日志会报清理条数。

字面 `<text>`）、思考块的 6 种形态、未闭合不吃正文、端到端落库、存量清洗幂等、默认值不变式
（含"schema 与代码两处默认值必须一致"）。

### v2.11.1 (2026-09-12) — 修三个索引问题：回填卡死 / 候选集不全 / 索引其实没被用上 🔧

合并 v2.11.0 后用户报：**界面一直显示「索引 回填中」**，同时 `on.im_message` 钩子刷 `AttributeError` 日志。
查下去发现 v2.11.0 的索引有三个问题（前两个会让它**看起来在工作、其实在漏召回**）：

1. **回填循环永不结束**（就是「一直回填中」）。根因：摘要为空 / 只有标点（算不出索引体）的记录，
   `search_body` 永远是 `''`，而 `''` 正是「还没进索引」的判据 → 每批都把同一批行捞出来，卡死并空转 CPU。
   现在这类摘要写占位符 `-`（FTS 分词器对它不产生任何词元，永不命中；这些行的词面得分本来就恒为 0），
   处理过就不再被捞出来。回填失败也不再留在 `building`（显式降级为 `unavailable` 并说明原因），
   成功则用 **info 日志报出补齐条数**——"到底好没好"一眼可见。
2. **候选集不是打分结果的超集**（真·漏召回）。索引体只有双字滑窗：单字查询「猫」查不到「…欢猫」；
   跨词边界子串「iph」查不到「iphone」。现在索引体收录**每个单字 + 每一对相邻字**，
   查询侧对 ≥3 字词元做同样的拆对 → 只要词元出现在摘要里，它的某个 n-gram 一定在索引里，候选集恒为超集。
   新增**子串全覆盖属性测试**：对一段文本的每个子串查询，逐一比对「索引路径 vs 全表路径」。
   索引体口径变了，存量库**自动重算**（`meta.search_index_scheme`，后台作废旧索引体再回填，不阻塞启动）。
3. **索引其实没被用上**（顺手查出来的）。SQL 里写的是 `(search_body='' OR rowid IN (…))`，
   SQLite 因为那个 `OR` 放弃 rowid 索引、退化成全表扫描：同一条查询 **0.28ms → 18ms**，等于白建。
   现在候选条件只保留纯 `rowid IN (…)`，"还没进索引的行"由 `_fts_hits` 直接并进候选列表
   （并给 `search_body=''` 加部分索引，那次探测从 18ms 降到 0.1ms）。

**顺带修**：① `on.im_message`（单条消息事件）里预热钩子直接崩——`KiraMessageEvent` 只有 `.message`
（没有 `.messages`），且**没有 `.sid`**（要走 `.session.sid`），等于预热一直算在 `""` 这个假会话上、永远命中不了缓存；
② 写入时**就地算好索引体**（原来 `capture` / 压缩归档 / 永久记忆 / 迁移导入都只写 `summary`，
新记录要等下次启动回填才进索引）；③ 编辑摘要 / 恢复旧版本时同步刷新索引体（否则那条会静默离开候选集）。

**实测（12,000 条存档，与全表路径逐条一致 ✓）**：`海龟汤` 64.9 → **17.7ms（3.7×）**；
`星月最近怎么样` 116.1 → **21.9ms（5.3×）**；`草莓蛋糕和咖啡` 136.5 → **21.9ms（6.2×）**；
命中过宽的单字查询自动退回全表（0.9×，只多几毫秒）。**修正 v2.11.0 的实测结论**：
当时那组数字主要来自打分下推，索引本身并没有真正生效（原因见第 3 条）。

测试：默认 222 passed 8 skipped；KIRA_CORE 266 passed；web_audit 0。

### v2.10.0 (2026-09-11) — 召回提速：打分下推到 SQL + 并发 + 缓存 + 预热 ⚡

先用基准量出瓶颈（2 万条存档 / 1200 条事实）：

| 调用 | 改前 | 改后 |
|---|---|---|
| **词面检索**（最大头） | **1,221 ms** | **355 ms** |
| 事实词面匹配 | 65 ms | 22 ms |
| 其余（context / 常驻事实 / 名字） | ~100 ms | 命中缓存后 ≈ 0 |

- **根因**：`relevance()` 每被调用一次就**重新切一遍查询词元**，而它是注册进 SQLite 逐行回调的
  —— 2 万行 = 2 万次分词 ✗。现在把「词元命中 × 词长」的求和**整段下推成 SQL 表达式**
  （`instr` 纯 C 层），排序也用同一个表达式；**打分口径与原来完全一致**
  （有专门的等价性测试钉住：SQL 打分必须等于 `relevance()`）。
- **并发**：注入路径开头三个互不依赖的查询（上下文 / 名字保护表 / 实体解析）改 `asyncio.gather`。
- **进程内缓存**：只缓存「不随消息变化」的（上下文、名字保护表），按 store `revision` 失效
  （写入即失效，`touch_accessed` 不 bump，所以不会每轮抖动）。
- **预热**：消息一到（`on_im_message`）就预热该会话，把耗时挪到「打字 + 网络往返」期间；
  同会话 2 秒内只一次。
- **时间预算（默认关）**：`inject_budget_ms`，超过预算只跳过两个**可选通道**
  （跨会话存档检索、内容匹配召回），**核心召回一条不少**；默认 0 = 不限制，质量优先。
- **索引**：`facts(deleted,merge_pending)`、`records(permanent) WHERE permanent=1`。

实测真实注入路径（6000 条存档）：**394 ms（冷）→ 312 ms（热）**；用户当前规模（百条级）是 ms 级。

**仍未做的**：FTS5（`tokenize='trigram'`）能把全表子串扫描再降一个数量级，但需要建虚拟表 + 触发器同步 + 迁移，留作后续；向量路径（默认关闭）的逐行相似度回调同样待批量化。

### v2.4.0 (2026-09-09) — 原始对话不再重复注入 🪶

- **未压缩的最近原文（L0）默认不进每轮记忆块**：KiraAI 的上下文里本来就有这些对话，重复注入只会膨胀。实测（60 轮会话）注入块从 **22.6 KB 降到 0.3 KB**，与宿主历史的重复从 **100 条降到 0 条**；压缩后也从 9.8 KB 降到 0.46 KB。
- 需要时模型用 `SearchMemoryArchive` / `ReadMemoryArchive(id)` 主动检索；跨会话被动召回不受影响（其他会话的相关内容照常带入）。
- 新增配置 `inject_recent_raw`（默认关）可恢复旧行为。
- 顺带提升提示词缓存命中：注入块挂在最后一条消息里，块越小，每轮"未命中尾巴"越短。

### v2.3.1 (2026-09-09) — 迁移不再阻塞启动 ⚡

- 旧记忆迁移改为**后台执行**：`initialize()` 不再等待迁移完成，插件加载不被拖住；迁移期间记忆功能照旧暂停，完成后自动恢复。
- 源文件没有变化、且没有旧插件在运行时，启动时**跳过重扫**（只 stat 文件、不解析 TOML）；旧插件被重新启用或源文件有更新时会自动重新迁移。
- 迁移成功记录时间戳，失败不记录（下次启动继续重试）。

### v2.3.0 (2026-09-09) — 旧历史播种保护 🛡️

- 新增配置 `bootstrap_seed`（默认 `auto`）：首次遇到旧会话时是否把 KiraAI 已有历史抄进记忆库。`auto` 在检测到会话合并/压缩插件（KSM / ADS / Context Condensation）启用时**跳过播种**，避免把别的会话的对话记成本会话的经历；`always` 始终播种；`off` 从不播种。
- 播种状态改为显式记录（`meta.bootstrap:<sid>`），清理后不会重新播种，会话记录被归档清空也不会重复播种。
- 播种时写入「干净标记」`meta.bootstrap_clean:<sid>`（仅当时没有合并插件时），启动时只对**来源无法确认**的遗留记录提示核对：概览页提示条 + 「去清理」/「保留，不再提醒」，不自动删除。
- 后台任务页新增 **「清理历史播种记录」**：软删除安装时抄进来的旧对话（原文保留在版本快照里），并顺带清理只由这些记录支撑的事实。
- 文档重写：前言、机制、配置、兼容性与致谢。

### v2.2.6 (2026-09-09) — 合并诊断与审计限流 🔍

永久记忆合并的任务详情现在写明原因：`常驻 N 条 · 相似簇 K 个 · 合并 M 簇 · 保留 J 簇`，并在没有可合并对象时说明「常驻不足 2 条（含已归档 N 条）」或「未发现相似簇（阈值 0.25）」。手动按钮与自动调度走同一逻辑，因此两边都能看到。

后台审计改为**每个间隔只处理最久未审计的 `worker_count` 个会话**，不再给每个会话都入队，导入大量旧记忆后也不会让后台一直满负荷；审计任务详情显示「本次审计 N 条事实」。

详见[永久记忆合并的诊断信息](docs/DEDUPE_DIAGNOSTICS_2_2_6.md)。

### v2.2.5 (2026-09-09) — 检测到相似就强制合并 🔗

相似永久记忆**检测到就强制合并**：以最新那条为基准，把其余各条独有的信息全部并入；模型若仍想保留，程序会用原文拼接兜底合并。新增开关 `dedupe_force_merge`（默认开），关闭则回到"只在确属重复或更正时才合并"的保守策略。

详见[检测到相似就强制合并](docs/FORCE_MERGE_2_2_5.md)。

### v2.2.4 (2026-09-09) — 同一会话只给新情报 🆕

同一会话只给新情报：搜索默认排除本会话已经给过的记忆（含每轮注入的存档与事实、按 ID 读过的存档），只返回新内容；`already_seen` 报告跳过数量，`allow_seen=true` 可显式重搜，`ReadMemoryArchive(id)` 永远能重读。`MemoryOverview` 的事实同样去重，每次最多返回 50 条新事实。同时删除写死的「还有别的吗」启发式（`re.fullmatch` 只认 8 个固定短语），改由模型通过 `SearchMemoryArchive(next_batch=true)` 驱动。

详见[同一会话只给新情报](docs/NEW_ONLY_RECALL_2_2_4.md)。

### v2.2.3 (2026-09-09) — 永久记忆去重与冷归档 🧊

永久记忆不再重复堆积：`Memorize` 遇到完全相同的永久记忆直接返回已有条目（被 Forget 过的会恢复），不新增；新增后台任务 `dedupe` 用**审计模型**检查相似的永久记忆，确属同一件事的重复或更正时自动合并——保留最新一条、其余移出常驻上下文（原文与版本保留）。开关 `permanent_dedupe`（默认开）与阈值 `dedupe_threshold`（默认 0.25）可在设置页热更改；后台任务页可手动触发。

**检索范围**：默认只搜活跃记忆，已归档的旧记忆需要显式 `include_archived=true` 才返回（结果带 `archived` 标记）；配置项 `search_active_only` 默认开启，关闭则恢复旧行为。对齐 Alife 原版"不翻旧账"的语义。

**冷归档**：被 Forget 或被合并取代的记忆立即冷归档；归档满 `cold_after_days`（默认 180 天）后自动冷归档。冷归档**任何检索都搜不到，只能按存档 ID 读取**，原文与版本全部保留，WebUI 可一键恢复常驻。

详见[永久记忆去重与自动合并](docs/PERMANENT_DEDUPE_2_2_3.md)、[检索范围](docs/ARCHIVE_SCOPE_2_2_3.md) 与 [冷归档](docs/COLD_ARCHIVE_2_2_3.md)。
